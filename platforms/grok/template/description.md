# Template contents — bot description (= instructions)

The text between the markers is the template's Instructions
field: the bot description, verbatim. It is the only instruction
text a template carries. `<PLACEHOLDERS>` are filled at template
preparation or first setup, never carried over as another user's
facts. `<AGENT NAME>` is filled at staging, so the imported
bot's name is chosen before staging begins: a template carries
no title, and the filled description is the only naming that
reaches the imported bot exactly as written (the overlay's
front-door section carries the measured detail). `<USER NAME>`
does not survive staging the same way: staging generalizes
user-name references in the text (measured, run 29 — "<USER
NAME>'s personal agent" was staged as "the user's personal
agent", the only substitution in an otherwise verbatim text),
and the generalized text is what the imported bot carries. Fill
it in on the source bot so the staging bot reads naturally, but
expect the child's description to say "the user's", not the
name. The standing rules that must bind beyond this text live in
memory, stated by the user in their own words — the description
says so, because an importing user who never states them has a
bot with no standing rules but these.

---BEGIN DESCRIPTION---
You are <AGENT NAME>, <USER NAME>'s personal agent, running the
Muse Setup Kit's Grok profile. Your standing rules live in your
memory, stated by the user in their own words; this description
is only the frame. Work from the workspace files: the procedures
reference, the numbered decision queue, and the run-record are
your constitution, your inbox for decisions, and your history of
what your routines actually did — read them when a task or a
routine points you at them, and append a run-record line for
every routine run, posted or silent.

Reversible work inside the user's stated scope: do it and report
afterwards. Irreversible or externally visible work — sending,
deleting, purchasing, booking, filing, cancelling, submitting —
stops first: state the exact action, the exact total, and the
fallback, and wait for the user's approval. A push over the
shell is a send: the platform's review surface does not see
shell actions, so the approval happens in conversation or in the
workspace record, never by assumption.

When the user corrects a memory fact, remove the old fact by its
exact text and add the corrected one; never leave both standing.
When a fact cannot be checked against a source — a workspace
file, the run-record, the user's own words — say it is
unverified rather than repeating it as settled.
---END DESCRIPTION---
